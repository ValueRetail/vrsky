    Cloud storage (S3 / Azure / GCS)¶

    The cloud storage connector reads from and writes to object stores. A single connector kind (cloud_storage) covers Amazon S3, Azure Blob Storage, and Google Cloud Storage; the provider field selects the backend and which credential fields apply.

    Provider Credential fields
    s3 access_key_id + secret_access_key. Unless both are set, the AWS default credential chain applies (environment, role).
    azure connection_string, or account_name + account_key.
    gcs credentials_json (service-account JSON). With an endpoint and no JSON, no credentials are sent (the emulator).

    As a source (consumer)¶

    A consumer node lists objects under prefix in the configured bucket and downloads them as messages. By default it polls; set mode to event to receive object-created notifications instead (S3 → SQS, Azure → Storage Queue, GCS → Pub/Sub) for low-latency, event-driven ingestion (#106).

    Config bullets (all under cloud_storage):

    • provider — s3 (default), azure, or gcs.
    • bucket — the bucket (S3, GCS) or container (Azure) to read from. Required.
    • prefix — key prefix to scope the listing (e.g. incoming/). Empty means the whole bucket. The listing is recursive: objects under deeper keys (incoming/2026/a.csv) are ingested too. In event mode it selects the keys a notification names, in the same way (see below).
    • region — provider region (S3).
    • endpoint — custom endpoint: MinIO or another S3-compatible store (path-style addressing is then used), or a private or emulated GCS endpoint.
    • Credentials — per-provider, as in the table above.
    • mode — poll (default) or event for notification-driven reads.
    • poll_interval_seconds — poll mode: seconds between listings. 0 or unset means one listing, after which the connection shows as stopped. A new poll-mode source in the editor saves 60 here without you touching the field. A node saved before that change (#589) has no value and lists once: open it, press Save Configuration so it gets the 60, and redeploy. Type 0 to choose one listing on purpose.
    • file_pattern — glob matched against the object's base name (the part after the last /), e.g. *.csv. Empty means every object. Applies in both modes.
    • after_action — what to do with an object once it is published: none (default, leave it), delete, or move. Applies in both modes.
    • move_prefix — where move puts the object: it is copied to <move_prefix>/<base name>, then deleted. Required with move; without it the consumer doesn't start. Moves keep only the base name, so incoming/a/x.csv and incoming/b/x.csv both land on <move_prefix>/x.csv and the second overwrites the first.

    In poll mode the start is also refused when prefix would select moved objects again (#567). The log says invalid move_prefix and names both values. Event mode starts anyway, with a warning (below). prefix is matched as text, not as a folder: - Starts: prefix: incoming/ with processed/, incoming-done/ or . (the bucket root); prefix: incoming/a/ with incoming (one level up). - Refused: move_prefix equal to or under prefix (incoming/, incoming/done/); any move_prefix with an empty prefix (the whole bucket); prefix: incoming without the / and incoming-done/ (incoming lists incoming-done/… too); prefix: data/report_ with data (data/report_1.csv would move onto itself).

    For the bucket root use ., not /: a move keeps a leading slash, so / puts x.csv at the key /x.csv, which S3 and GCS keep as a separate key from x.csv. The check resolves . and .. the way the move does but ignores leading slashes, so it may refuse a config with a leading / that would have worked on S3 or GCS. In both modes the consumer never moves an object onto its own key: that move fails with after-action failed in the log and the object stays where it is.

    In event mode a moved object sends a new notification, and prefix is what keeps it out. When the same rule finds move_prefix inside prefix (an empty prefix included), an event-mode connection still starts and logs a warning, move_prefix is inside prefix; starting anyway in event mode. A moved key is always <move_prefix>/<base name>, so if its notification reaches the queue the object is published once more, the move onto its own key is refused (after-action failed, already in move_prefix), and it stays in move_prefix: one duplicate, no loss, no loop. To avoid the duplicate, set a prefix with move_prefix outside it, or scope the bucket notification so moved objects don't reach the queue.

    Event mode also reads:

    • event_queue_url — S3: the SQS queue URL. Required.
    • event_queue_name — Azure: the Storage Queue name. Required.
    • event_subscription — GCS: the Pub/Sub subscription, as a full path or a bare name. Required.
    • event_project — GCS: the GCP project ID. Required when event_subscription is a bare name.
    • event_endpoint — optional endpoint for the queue or Pub/Sub service (LocalStack, Azurite, the Pub/Sub emulator). Not the object-store endpoint. On GCS it also turns off authentication and TLS for Pub/Sub, so use it only for the emulator. On Azure it is used only with account_name + account_key; with connection_string the queue address comes from the connection string.

    In event mode prefix and file_pattern apply to the keys a notification names, as in poll mode (#594). prefix is matched as text, so in also selects in-done/a.csv; file_pattern is matched against the base name. A key outside them is acknowledged and skipped: nothing is published, moved or deleted for it and the message is not redelivered. The first skipped key of each run of the connection is logged at Info level (event key outside prefix or file_pattern; skipped, with the key, prefix and pattern), later ones at Debug. Folder placeholders (keys ending in /, which the S3 console's "Create folder" writes) are skipped as in poll mode. Keys are matched after decoding, so an S3 key in+folder/a.csv is matched as in folder/a.csv. The editor shows File pattern in both modes. You can still scope the bucket notification itself to cut the traffic, but you no longer have to for correctness.

    Only object-created events are ingested, on every provider: BlobCreated on Azure, OBJECT_FINALIZE on GCS, and ObjectCreated:* on S3 (Put, Post, Copy and CompleteMultipartUpload). MinIO's metadata events under ObjectCreated (PutTagging, DeleteTagging, PutRetention, PutLegalHold) are not creates. Other S3 records (removals, lifecycle, restore, tagging) are acknowledged and skipped too. Before #594 the S3 consumer ingested every record in a notification, and an event-mode connection ignored prefix and file_pattern; a connection that relied on that now skips what its prefix or file_pattern does not select. That includes a file_pattern saved while the connection was in poll mode, which the editor used to hide in event mode: check it after the upgrade.

    {
  "type": "cloud_storage",
  "cloud_storage": {
    "provider": "s3",
    "bucket": "my-bucket",
    "prefix": "incoming/",
    "region": "us-east-1",
    "access_key_id": "AKIA...",
    "secret_access_key_secret_id": "sec_s3key_01",
    "mode": "event",
    "event_queue_url": "https://sqs.us-east-1.amazonaws.com/123456789012/vrsky-incoming",
    "after_action": "move",
    "move_prefix": "processed/"
  }
}

    What gets published, and when again (poll mode)¶

    In poll mode the consumer remembers which objects it published, with the size and last-modified time each had, in the connection's checkpoint (one per tenant, connection and node). It survives restarts, deploys and the nightly park, so with after_action: "none" an object left in the bucket is published once, not again at every start (#538).

    • First start. Every object already under the prefix is published. A start after the provider, endpoint, account, bucket or prefix was edited counts as a first start too.
    • Replaced object. An object overwritten under the same key (its size or last-modified time changed) is published again, once.
    • Deleted, then added again. An object that a poll finds gone from the listing is forgotten; if it comes back it is published again.
    • Failed after-action. If delete or move fails, the object is still counted as published and stays where it is; it is not published or moved again, also after a restart. The failure is in the log (after-action failed).
    • Checkpoint unreadable. If the database can't be read at start, the consumer publishes nothing and logs Could not read which objects were already published. It tries again at every poll and carries on as normal once the read works. A one-shot connection (poll_interval_seconds: 0) ends with status error instead.
    • Crash. The list is saved every 32 objects and at the end of each poll, so a crash in the middle of a long poll publishes at most the objects since the last save again.

    An object replaced with the same size within the same second (S3 keeps last-modified times in whole seconds) looks unchanged and is not published again. Event mode doesn't use this list: there the queue's acknowledgement decides what was handled.

    After the release that added this, each running poll-mode connection's first start has no saved list yet, so it publishes what is under its prefix once more, as every restart did before.

    As a destination (producer)¶

    A producer node writes each incoming message as an object under prefix in bucket. Server-side encryption can be set per node (#80) via the sse block: none, sse-s3 (S3-managed keys), or sse-kms (supply kms_key_id).

    Config bullets:

    • provider, bucket, prefix, region, endpoint — as above.
    • Credentials — per-provider.
    • sse.mode — S3 only: none (default, the bucket's own setting), sse-s3, or sse-kms. Azure and GCS don't read it.
    • sse.kms_key_id — on S3, the KMS key ID or ARN for sse-kms; without it, sse-kms uses the AWS-managed key. On Azure (an encryption scope name) and GCS (a Cloud KMS key name) it is applied whenever it is set, whatever sse.mode says, so clear it to go back to the bucket's default.
    • key_template — Go template for the object key, rendered against the record when it is a JSON object plus {{.timestamp}} and {{.uuid}} (default {{.uuid}}). Pictures and other media (images, audio, video, PDF) that carry a filename ignore the template and are written as <prefix>/<filename> — the same rule as the file and remote-agent destinations, so 1896-S.jpg stays 1896-S.jpg next to the records.
    {
  "type": "cloud_storage",
  "cloud_storage": {
    "provider": "azure",
    "bucket": "my-container",
    "prefix": "outgoing/",
    "account_name": "mystorageacct",
    "account_key_secret_id": "sec_azkey_01",
    "sse": { "mode": "none" }
  }
}

    Notes¶

    • Secrets. Credentials typed in the UI (secret_access_key, connection_string, account_key, credentials_json) are minted into encrypted tenant secrets at deploy and replaced with <field>_secret_id references — they never appear in plaintext in the stored connection. Non-secret fields like access_key_id and account_name are stored as-is.
    • Test connection. The cloud-storage worker exposes a /test-connection endpoint; use the Test connection button in the editor to verify bucket access before deploying.
    • Object-format handling and any provider-specific options not listed here are configured via the in-app pipeline editor (Property panel).
