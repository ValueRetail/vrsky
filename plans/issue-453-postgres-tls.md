# #453 TLS between the services and Postgres

Production talks to its in-cluster Postgres in plain text: the Secrets say
`sslmode=disable` and the server has no certificate. Ludvik decided on
2026-11-02 (in #453): TLS on the in-cluster Postgres with a cert-manager
certificate, not a managed Postgres. Backlog item 58.

The PR touches manifests, Secrets handling and the backup job, so it gets
`agent:needs-human`, and a human merges it and runs the rollout below. This
agent did not touch the cluster for any of it (one slip is in
[What happened in the session](#what-happened-in-the-session)).

## Open questions

None block the PR. Each has a default the PR already follows; say so if you
want one changed.

1. **Postgres restarts once** (a minute or more with no database, step 2: the
   disk detaches and re-attaches).
   Default: do it right after `az aks start`, when nothing is happening.
2. **Is cert-manager in production recent enough?** The repo installs v1.13.3
   (`install-cert-manager.sh`); the manifests use `cert-manager.io/v1` only.
   Step 0 prints what is there.
3. **Refuse plain connections too (`hostssl`)?** Default: not in this PR's
   rollout. It is step 10, optional, after a few days with no plain
   connection. The PR documents and rehearses the command; it is not in a
   manifest (backlog item 156).
4. **No alert on certificate expiry.** cert-manager's metrics are not scraped
   here. The certificate is renewed 90 days before it ends and picked up at
   the next Postgres start (every cluster start), and `postgres-tls.sh check`
   says when Postgres still serves an older one. An alert is backlog item 156.

## Goal

Every platform connection to the management Postgres is encrypted and
checked: `sslmode=verify-full` against a private CA, with no outage on the way
and a rollback that is a Secret edit.

## Design

```
Issuer postgresql-selfsigned -> Certificate postgresql-ca (isCA, 10 y)
  -> Issuer postgresql-ca -> Certificate postgresql-tls (server, 1 y, renew at 90 d left)
  -> Secret postgresql-tls { tls.crt, tls.key, ca.crt }
init container copies tls.crt + tls.key into a memory volume as uid 70, 0600
postgres -c ssl=on -c ssl_cert_file=... -c ssl_key_file=...
ca.crt (public) -> ConfigMap postgres-ca in vrsky-platform and vrsky-database
every client mounts it at /etc/vrsky/postgres-ca; the string says
  ?sslmode=verify-full&sslrootcert=/etc/vrsky/postgres-ca/ca.crt
```

Decisions, each of which I made without asking:

- **Names on the certificate:** `postgresql`, `postgresql.vrsky-database`,
  `.svc`, `.svc.cluster.local` (the Service is `postgresql`; checked in
  `service.yaml`) and `localhost` + `127.0.0.1`, so `kubectl port-forward` and
  `exec` can use `verify-full` too. It is only valid for clients that trust
  this private CA.
- **Key and mode:** `fsGroup` would make the Secret volume readable but also
  turns the data directory group-writable (kubelet adds the group write bit),
  and Postgres then refuses to start. An init container copies the pair into
  an `emptyDir` with `medium: Memory`, `chmod 0600`, `chown 70:70` (uid/gid 70
  is `postgres` in the Alpine image, as the backup CronJob already assumes). It
  has only `CAP_CHOWN`; chmod comes before chown because after chown the
  container is no longer the owner and has no `CAP_FOWNER`. The key never
  touches a disk.
- **Renewal:** cert-manager rewrites the Secret 90 days before the end. The
  copy is made at pod start, so Postgres serves the new certificate from its
  next start. All production pods restart at every cluster start
  ([cost-parking](../docs/operator/cost-parking.md): "Running pods: No, all
  evicted, recreated on start"), so renewal is picked up long before expiry.
  I did not add a reload sidecar: it is a second container and a shared
  process namespace to get right, for a restart that already happens. If the
  cluster runs 90 days without a start, `postgres-tls.sh check` flags the old
  certificate and `kubectl rollout restart statefulset/postgresql -n
  vrsky-database` fixes it. The CA lasts ten years, keeps its key on renewal,
  and clients hold its certificate, so `ca-sync` has a year to run again
  (`check` compares the copies).
- **Distributing the CA:** trust-manager is not installed and cert-manager
  cannot copy Secrets across namespaces. `postgres-tls.sh ca-sync` copies
  only `ca.crt` (public) into a ConfigMap in each client namespace. Issuing
  per namespace would give different CAs; trust-manager is another operator
  for one file. The ConfigMap volumes are `optional`, so merging first and
  copying later is safe, and a pod never waits for it.
- **Where the mounts land:** the connectors and the backup CronJob get theirs
  from the deploy job when this merges (their manifests change). The deploy
  job only sets images on management-api, data-filter and data-converter, and
  the docs forbid `kubectl apply` of those manifests (they name ghcr images),
  so `postgres-tls.sh clients` adds the volume by strategic-merge patch,
  leaving the image alone. The manifests carry the same volume for k3d and
  rebuilds.
- **Order:** the server accepts TLS and plain (`pg_hba.conf` unchanged,
  `host` rules), so any client order works. The plan is: server, CA, mounts,
  canary, strings, restarts, then (optional) `hostssl`.
- **No printing:** the script reads a connection string into a shell
  variable, changes only the `sslmode` and `sslrootcert` parameters, and
  patches the Secret through stdin (`--patch-file /dev/stdin`), so the value
  is neither on screen nor in `ps`. `urls verify-full` refuses to run unless
  Postgres has `ssl = on`, the CA ConfigMaps exist, and every connector,
  core Deployment and the backup CronJob mount the CA. Fail closed.
- **`sslmode=disable` that stays:** the two dev `secret.example.yaml` files
  (k3d does not copy the CA), the ad-hoc DR scratch pod, CI and compose.
  `TestPostgresTLS_NoClientSaysSSLModeDisable` lists the exceptions.
- **k3d and rebuilds:** `deploy-vrsky-platform.sh` installs cert-manager when
  the CRD is missing and applies `tls.yaml` before the StatefulSet.
  `rotate-secrets.sh` now writes `verify-full`, runs `ca-sync`, and stops if
  Postgres has no TLS.

## Risks

| Risk | What happens | Mitigation |
| --- | --- | --- |
| A client without the CA on `verify-full` | that service cannot reach the database after its next restart | `urls verify-full` refuses until every client mounts it; the canary proves the path first; `restart` goes one deployment at a time, management-api first; a rolling update keeps the old pod until the new one is Ready |
| Postgres does not start after step 2 | the control plane is down until fixed | the init-container logic was rehearsed on `postgres:18-alpine` with the same caps and args (below); step 2 starts with a dry run and a diff; `kubectl rollout undo statefulset/postgresql -n vrsky-database` plus `kubectl -n vrsky-database delete pod postgresql-0` goes back (a rolling update does not replace a pod that never became Ready; the disk re-attach can take longer than a minute) |
| Certificate expires | `verify-full` clients fail everywhere | 1-year certificate, renewed at 90 days left, picked up at the next start; `check` flags a stale copy; no alert yet (backlog 156) |
| The CA certificate renews and a ConfigMap is stale | not for ten years; clients keep verifying against the old certificate until it expires | `check` compares the copies; run `ca-sync` |
| Restart of Postgres drops connections | a minute or more of errors | do it right after cluster start; services reconnect on their own, as at every start |
| Drift in the live StatefulSet | `apply` also applies unrelated differences, or fails on immutable fields | step 2 shows `kubectl diff` first; a failed apply changes nothing |
| `rotate-secrets.sh` on a cluster without TLS | would write strings nothing can serve | it checks `SHOW ssl` and aborts |
| k3d path is untested here | `deploy-vrsky-platform.sh` now needs cert-manager | it installs it when the CRD is missing; the dev Secrets stay `disable` so a failure of the CA copy cannot break k3d |
| Backup job | `pg_dump` fails on `verify-full` without the CA | `BACKUP_DB_URL` is switched by `urls` in the same step as the rest; the manual job in step 9 proves it before the next scheduled run |

**Rollback:** `postgres-tls.sh urls disable` then `postgres-tls.sh restart`.
The server accepts plain and TLS, so nothing on the server needs undoing. If
`hostssl` was turned on (step 10), undo it first.

## How we verify it

Done in this PR, with no cluster:

- Guard tests (`go test -count=1 ./pkg/managementapi/ -run TestPostgresTLS`):
  the StatefulSet turns `ssl=on` on and mounts the cert and key from the Secret
  the Certificate writes, with the init container's `chmod 0600` before
  `chown 70:70` and a memory volume; the Certificate lists the Service's DNS
  names and chains to the CA Issuer; every workload that reads the connection
  string (found by what it reads, 35 or more today) mounts the CA; the
  connection string `rotate-secrets.sh` builds says `verify-full` with the CA
  path and the script checks `SHOW ssl`; no manifest, script or backup doc
  says `sslmode=disable` except the listed exceptions; `retarget_url` changes
  only `sslmode` and `sslrootcert`; the script never prints a URL.
- The script itself runs in tests against a `kubectl` stand-in that only logs
  its arguments (`postgres_tls_script_test.go`; `KUBECONFIG=/dev/null`, and the
  test refuses to run unless the stub is the only `kubectl` on `PATH`): no
  subcommand writes without `CONFIRM=1`; `DRY_RUN` and `check` write nothing;
  `ca-sync` exits 0 under `/bin/bash` (3.2 on the Mac); the canary pod is
  deleted last whether the canary passes or fails; `restart` and `urls
  verify-full` stop when the connector list is empty, short of 31, or fails.
- Rehearsal on `postgres:18-alpine` in Docker: an init container with
  `--cap-drop ALL --cap-add CHOWN` left the key `70:70 0600`; the server
  started with the same `-c` arguments; `psql` with `verify-full` and the CA
  connected over TLSv1.3 through `localhost` and through the Service's DNS
  name; a wrong host name and a missing CA file were refused; `sslmode=disable`
  still worked; both `lib/pq` and `pgx` connected with the same URL; after the
  `hostssl` edit and a reload a plain connection from another container was
  refused (`no pg_hba.conf entry … no encryption`) and the TLS one worked.
  The container ran with test values only.
- Not done: nothing here ran against cert-manager or the cluster, so the
  Issuer/Certificate chain is checked by the tests for shape, not by
  cert-manager. Step 2 shows it.

## Steps for Ludvik

Run from a checkout of main after the merge. `postgres-tls.sh` never prints a
connection string. Every subcommand except `check` prints the kube context
and refuses to run unless `CONFIRM=1` is set, so look at the context line, then
run it with `CONFIRM=1`. `DRY_RUN=1` prints what a step would do and needs no
`CONFIRM`. Run `postgres-tls.sh check` between steps; it only reads.

**Step 0, before anything (read-only)**
```bash
kubectl config current-context                       # vrsky-prod
kubectl get crd certificates.cert-manager.io         # exists
kubectl -n cert-manager get deploy                   # cert-manager, cainjector, webhook ready
infrastructure/azure/postgres-tls.sh check
```
Expect: no certificates, `ssl = off`, all connections `ssl=false`, strings
`disable`, and the core Deployments listed as "NO postgres-ca volume".

**Step 1, merge the PR.** The deploy job rolls the connectors with the CA
mount (no behaviour change: the mount is optional and nothing reads it yet)
and updates the backup CronJob. If the cluster is parked, start it first and
let Production check roll it forward. Then `check` should list only the three
core Deployments under "clients that mount the CA" (no connector, not the
backup job).

**Step 2, TLS on the server.** Best right after a cluster start. The dry run
prints `kubectl diff` of the StatefulSet against the live one: read it before
you confirm. It should show only the init container, the `args`, the two
volumes and the mount; anything else is drift in the live object, and the
apply would change that too.
```bash
DRY_RUN=1 infrastructure/azure/postgres-tls.sh server   # read the diff
CONFIRM=1 infrastructure/azure/postgres-tls.sh server   # certificates Ready, StatefulSet restarts, prints "ssl is on"
infrastructure/azure/postgres-tls.sh check
```
Expect: both certificates `Ready: True`, "Postgres serves the Secret's
current certificate", `ssl = on`, connections still `ssl=false`. The restart
takes a minute or more: the disk detaches and attaches again.
Failure: `kubectl -n vrsky-database logs postgresql-0 -c tls-perms` and
`-c postgresql`. To go back, `kubectl -n vrsky-database rollout undo
statefulset/postgresql` and then `kubectl -n vrsky-database delete pod
postgresql-0`: a rolling update does not replace a pod that never became Ready,
so without the delete the old spec is never started.

**Step 3, copy the public CA.**
```bash
CONFIRM=1 infrastructure/azure/postgres-tls.sh ca-sync
infrastructure/azure/postgres-tls.sh check              # both postgres-ca ConfigMaps "match the CA"
```

**Step 4, mount the CA in the three core services.**
```bash
CONFIRM=1 infrastructure/azure/postgres-tls.sh clients            # rolls management-api, data-filter, data-converter
infrastructure/azure/postgres-tls.sh check              # "all mount it"
```

**Step 5, canary.** One throwaway pod connects with `verify-full` and the live
Secret's host and password, and prints the session.
```bash
CONFIRM=1 infrastructure/azure/postgres-tls.sh canary             # prints "ssl=true TLSv1.3"
```
If it fails, stop: the strings must not change.

**Step 6, switch the strings.**
```bash
DRY_RUN=1 infrastructure/azure/postgres-tls.sh urls verify-full
CONFIRM=1 infrastructure/azure/postgres-tls.sh urls verify-full   # postgres-credentials in both namespaces, BACKUP_DB_URL
infrastructure/azure/postgres-tls.sh check              # the three strings say verify-full
```
Running pods still use the old value.

**Step 7, restart the clients.** One at a time; management-api first.
```bash
CONFIRM=1 infrastructure/azure/postgres-tls.sh restart
```
It stops at the first rollout that does not become Ready.

**Step 8, confirm.**
```bash
infrastructure/azure/postgres-tls.sh check              # "ssl=true" only; "WITHOUT ssl" empty
kubectl get pods -n vrsky-platform                      # all Ready
```
Give the pools a minute; then log in to the UI and open a connection. The
direct query, if you want it:
```bash
kubectl exec -n vrsky-database postgresql-0 -c postgresql -- psql -U vrsky -d vrsky -tAc \
  "SELECT s.ssl, count(*) FROM pg_stat_ssl s JOIN pg_stat_activity a USING (pid) WHERE a.backend_type = 'client backend' AND a.client_addr IS NOT NULL GROUP BY s.ssl"
```

**Step 9, the backup job.** Prove `pg_dump` over TLS before the next
scheduled run (it writes one more encrypted dump):
```bash
kubectl -n vrsky-database create job --from=cronjob/vrsky-mgmt-backup tls-check-1
kubectl -n vrsky-database wait --for=condition=complete job/tls-check-1 --timeout=600s
kubectl -n vrsky-database logs job/tls-check-1 | tail -5
kubectl -n vrsky-database delete job tls-check-1
```

**Step 10, optional, after a few days of no plain connections:** refuse them.
The commands are in `infrastructure/kubernetes/postgresql/README.md`
("Optional last step"). Undo is the opposite `sed` and a reload.

**Step 11, record it.** Fill in the rollout record below, close #453, strike
item 58 in `plans/backlog.md`.

**Rollback at any point after step 6:**
```bash
CONFIRM=1 infrastructure/azure/postgres-tls.sh urls disable
CONFIRM=1 infrastructure/azure/postgres-tls.sh restart
```

## What happened in the session

While testing the new `canary` subcommand I meant to run it against an offline
`kubectl` stand-in. The stand-in had not been created (the command that makes
it was refused), so `postgres-tls.sh canary` ran against the real kubeconfig
(`vrsky-prod`). It deleted a pod named `pg-tls-canary` that did not exist,
created that pod in `vrsky-platform`, polled it, and deleted it again. The pod
sat in `ContainerCreating` because the `postgres-ca` ConfigMap it mounts does
not exist yet, so its container never started and never read the Secret. I
could not confirm the deletion: the follow-up read was denied. Please run
`kubectl get pod pg-tls-canary -n vrsky-platform` (expect NotFound) and delete
it if it is there. Nothing else in this work ran against the cluster.
